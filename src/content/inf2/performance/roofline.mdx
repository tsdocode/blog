A roofline plots achieved throughput against **arithmetic intensity** (FLOPs per byte moved from HBM). For one
NeuronCore the two roofs are the Tensor Engine peak (~92 bf16 TFLOPS) and the measured HBM → SBUF bandwidth
(257 GB/s). They meet at about **360 FLOP/byte**: below that a kernel is bandwidth-bound, above it compute-bound.

A decode step with `B` tokens does 2 FLOPs per weight per token and reads each 2-byte weight once, so its intensity is
just `B` FLOP/byte. With 32 streams that is 32 — far below the ridge, so decode is a bandwidth problem no matter how
good the kernel is.

| Kernel (one core) | FLOP / byte | Achieved | Bound | Of its roof |
| --- | ---: | ---: | --- | ---: |
| Talker dense, 32 decode tokens | 32 | 8.2 TFLOPS (11.0 ms) | bandwidth | ~100% |
| Code predictor frame, 32 streams | 32 | 5.8 TFLOPS (14.3 ms) | bandwidth | ~70% |
| Talker step with 384 prefill tokens | ~416 | 27.7 TFLOPS (42.3 ms) | compute | ~30% |

How the points were computed: FLOPs = 2 × parameters × tokens (attention and other ops ignored); bytes = weight bytes
(KV-cache reads ignored). The talker has 1.41 B layer parameters (2.82 GB in bf16), the code predictor ~81 M read 16
times per frame.

## Reading it

- **Decode is done when it is on the bandwidth roof.** The talker's dense path is there; the only ways up are more
  streams per step (higher intensity) or fewer bytes per weight (FP8).
- **The code predictor has ~30% left** — its matmuls are small and its 16 steps are sequential.
- **Prefill is far below the compute roof** — attention, per-instruction overheads and the decode rows sharing the step
  all count against it.
- **The two cores have separate rooflines** but share HBM: both together measured ~508 GB/s, so running two engines
  does not halve either one's bandwidth.

Note that the 92 TFLOPS roof is the datasheet peak; see <T id="performance/matmul-cost">the matmul cost model</T> for
what limits real kernels below it.
