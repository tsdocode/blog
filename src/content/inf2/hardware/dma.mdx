Every byte that enters or leaves a NeuronCore goes through a DMA engine. Each core has **16 of them**, each able to
drive about 27 GiB/s, running in parallel with all the compute engines. A kernel's `nisa.dma_copy(dst, src)` becomes
one or more DMA **transfers**, and each transfer is a list of **descriptors**: one per contiguous chunk of memory.

## Descriptors are the cost

A descriptor describes one contiguous run of bytes. Copying a `[128, N]` tile into SBUF needs at least one
descriptor per partition, because partitions are separate memories. The guidance: make every contiguous run
large — 4 KiB or more along the free axis, across all 128 partitions.

The trap is that *the same number of bytes* can cost wildly different amounts. Writing into a strided slice of a
wider SBUF tile, for example, breaks every partition's run into many short pieces:

## Static vs dynamic

On NeuronCore-v2, descriptors for static access patterns are generated ahead of time and stored in HBM. Accesses
whose address depends on runtime data — a block id from a page table, a token id — use indirect addressing: a
runtime scalar offset for the whole transfer (`scalar_offset`) or a per-partition offset (`vector_offset`). Both
work for paged gathers and scatters, but each runtime-addressed transfer pays its own descriptor cost, so the trick
is to make every runtime transfer large.

## Practical rules

1. **Lay out HBM tensors so each partition's data is one contiguous run**, even if that means a less obvious
   tensor layout.
2. **Never DMA into a strided view.** Load into a contiguous staging tile, then copy on chip — on-chip copies are cheap.
3. **Batch runtime-addressed transfers**: one scatter for 128 tokens, not one per token.
