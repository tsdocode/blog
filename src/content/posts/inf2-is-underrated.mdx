Ask people what to serve a speech model on and you will hear "a GPU". Almost nobody says Inferentia2 — AWS's
inference chip, sitting in an instance that costs about the same as a single small GPU.

Over about 19 hours across two days I found out what it can actually do. I took
[nari-labs/nari-qwen3-tts](https://github.com/nari-labs/nari-qwen3-tts), a high-throughput serving engine for
[Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS) built for an H100, and ported it to one **inf2.xlarge**, writing the
hot path as hand-tuned kernels in AWS's kernel language, NKI.

The result: **64 concurrent streaming voices on one chip, each generated faster than real time** (real-time factor
0.79), **77× real time in aggregate**, and a steady-state p99 time to first audio of **279 ms**.

This post is how it actually went — compile, profile, replace each stage with a kernel, integrate, debug — and,
more than the final numbers, **how each problem was found**. Alongside it I wrote an
[**Inferentia2 Field Guide**](/blog/inf2/) — short, cross-linked pages that explain the chip one component at a time,
because almost nothing like it exists. Links in this post jump into it.

## The workload: three models per 80 ms

Qwen3-TTS (the 1.7B CustomVoice model) produces speech as codec frames: 12.5 frames per second, each frame 16
codebook tokens, each frame 80 ms of 24 kHz audio. Making one frame takes three models in sequence:

<Mermaid
title="One Qwen3-TTS frame"
chart={`flowchart LR
  T["Talker<br/>28 layers, 1.4B<br/>codebook 0"] --> C["Code predictor<br/>5 layers × 16 steps<br/>codebooks 1-15"]
  C --> D["Codec decoder<br/>transformer + convs<br/>1,920 samples"]
  D --> A["80 ms of audio"]
`} />

For a server, the constraint is brutal and simple: **every stream needs a new frame every 80 ms**. If one engine step
serves 32 streams and produces one frame for each, the whole step — talker, code predictor and codec for all 32 —
must take less than 80 ms, or playback stalls.

## The chip, in one picture

  <ChipDiagram />
</Diagram>

An Inferentia2 chip is two independent <T id="hardware/neuroncore-v2">NeuronCores</T> sharing 32 GiB of
<T id="hardware/hbm">HBM</T>. Each core has a 128 × 128 <T id="hardware/tensor-engine">Tensor Engine</T> (≈ 92 bf16
TFLOPS), a <T id="hardware/vector-engine">Vector</T>, a <T id="hardware/scalar-engine">Scalar</T> and a
<T id="hardware/gpsimd">GpSimd</T> engine — four instruction streams running in parallel — and a 24 MiB software-managed
scratchpad, <T id="hardware/sbuf">SBUF</T>. There are no caches: every byte that reaches an engine was moved there by
a <T id="hardware/dma">DMA</T> you asked for.

On paper the chip has 820 GB/s of memory bandwidth and 190 dense bf16 TFLOPS. I measured 257 GB/s into one core and
about 508 GB/s with both cores streaming. For comparison, an NVIDIA L4 lists 300 GB/s and 121 dense bf16 TFLOPS.

## Step 0: ground truth before speed

Before optimising anything I generated the answers I would check against: the upstream model run on the CPU in
fp32, greedy, on two prompts (22 and 74 frames) — the exact codec tokens and the audio. Every kernel and every engine
change after that was measured against this golden output, and against a layer-by-layer fp32 oracle for single kernels.

That mattered more than I expected. This talker drifts a lot in bf16 — upstream PyTorch in bf16 on the CPU diverges
from fp32 after a few frames too — so "matches fp32 exactly" is the wrong bar. The bar became **"as close to fp32 as
CPU bf16 is"**, checked with teacher forcing: feed the golden tokens back in and compare each step's prediction.

I also measured the hardware instead of trusting the datasheet: a streaming kernel moved **257 GB/s** into one core and
**~508 GB/s** with both cores at once. Those two numbers became the floor every kernel was judged against.

## Step 1: compile everything, then read the profiles

The first port was plain PyTorch, each component compiled with `torch.compile(backend="neuron")`, 32 streams per core,
timed with `torch.neuron.synchronize()` around the call:

| Component (32 streams) | Compiled |
| --- | ---: |
| Talker decode step | 29.6 ms |
| Code predictor, 16 depth steps | 73.5 ms |
| Codec decoder (fp32) | 37.5 ms |

A timer tells you it is too slow. The profiler tells you why.

### The tool: neuron-explorer

The Neuron SDK's profiler runs one compiled graph (a NEFF) on the device and records every instruction on every engine
and every DMA transfer, then turns the trace into tables:

```bash
# 1. run the graph on the device, record its 3rd execution
neuron-explorer capture -n model.neff -s trace.ntff --profile-nth-exec=3
# 2. trace -> parquet tables (Summary, OpcodeSummary, HloInstruction, ...)
neuron-explorer view -n model.neff -s trace_exec_3.ntff --ingest-only
# my wrapper: both steps + a one-screen summary
python neuron/tools/profile_neff.py model.neff --name cp-whole-b32
```

The summary's first line is the part I read first, every time:

- **device time** — how long the graph ran on the core;
- **HBM rd / wr** — bytes read from and written to device memory, and the effective read bandwidth (against the
  257 GB/s I measured as the ceiling);
- **engine busy %** — how much of that time the DMA queues and each compute engine were working.

Then the top instructions by time, per engine, with their counts. Here are the three profiles that decided the plan.

### Profile 1 — the code predictor, 16 steps unrolled into one graph

```text
[cp-whole-b32] device 70337.7 us
    | HBM rd 9979.57 MB wr 5548.84 MB | eff 142 GB/s read
    | DMA 88% TensorE 22% VectorE 22% ScalarE 17%            (one line, wrapped)
    tensor  MATMUL                 n=144806  15578.2 us
    tensor  LDWEIGHTS              n=141644  12336.3 us
    scalar  ACTIVATE               n= 42677  11731.1 us
    vector  COPY                   n= 22048   7319.3 us
```

**How to read it.** 70 ms on device and **15.5 GB** of HBM traffic — for a model whose weights are about 160 MB per
depth step, 2.6 GB per frame. Something is moving six times more data than the weights. DMA is 88% busy and every
compute engine is around 20%: the graph is waiting on data movement, not computing. The summary cannot say *which* op
moves the data, so the next query groups the `HloInstruction` table (bytes per compiled op) by op type:

```text
total HBM traffic attributed to ops: 12.72 GB
op           count   HBM GB   share
%scatter       320    12.20   95.9%
%slice         109     0.37    2.9%
%multiply     1403     0.06    0.5%
%dot           482     0.03    0.2%
```

**What it means.** 320 `scatter` ops moved 12.2 GB — 79% of all the traffic. They came from one innocent pattern in the
upstream model code: on non-CUDA devices, each depth step writes its new K and V into the cache **in place**
(`src/nari_qwen3_tts/model/components.py`):

```python
# before: one in-place slice write per layer, per depth step (unrolled 16x into one graph)
kv_cache[layer_index, :, 0, cache_pos:valid_length].copy_(key)
kv_cache[layer_index, :, 1, cache_pos:valid_length].copy_(value)
all_keys = kv_cache[layer_index, :, 0, :valid_length].transpose(1, 2)
```

A compiled graph is functional — it cannot update one slot of a buffer in place — so each `copy_` became a `scatter`
that produced a whole new cache. The numbers agree: 12.2 GB / 320 ≈ 38 MB per scatter, while the entire cache is
about 21 MB (5 layers × 32 streams × K/V × 16 slots × 8 heads × 128 × 2 bytes) — every write read and rewrote
essentially all of it.

The fix (`neuron/proto/cp_step_graph.py`): compile **one** depth step instead of 16, take the step index as a tensor
input so the same graph is reused for every step, and write the new slot with a mask instead of an in-place slice:

```python
# after: one reusable step graph; the step index is a tensor input
# which cache slot this step writes, and which slots attention may read
slot = (torch.arange(GROUPS, device=x.device) == step).view(1, GROUPS, 1, 1)    # GROUPS = 16
visible = (torch.arange(GROUPS, device=x.device) <= step).view(1, 1, 1, GROUPS)
...
# new cache = old cache with this step's slot replaced
kl = torch.where(slot, k.unsqueeze(1), kv[li, :, 0])
vl = torch.where(slot, v.unsqueeze(1), kv[li, :, 1])
new_kv.append(torch.stack((kl, vl), 1))   # returned as an output, never written in place
```

`torch.where` is an ordinary element-wise op the compiler streams through once, and the graph returns the new cache
instead of mutating its input. Compile time dropped from 567 s to 26 s and the frame from **73.5 to 32.1 ms** — which
made the next bottleneck visible.

### Profile 2 — the code predictor, one reusable step graph

```text
[cp-step-b32] device 1794.8 us
    | HBM rd 193.73 MB wr 23.27 MB | eff 108 GB/s read
    | DMA 66% TensorE 55% VectorE 33% ScalarE 60%            (one line, wrapped)
    scalar  ACTIVATE               n=  3249   1062.7 us
    tensor  MATMUL                 n= 19121    978.4 us
    tensor  LDWEIGHTS              n= 19040    786.1 us
    vector  TENSOR_SCALAR          n=  1294    358.4 us
```

**How to read it.** Now each step reads 194 MB — just the weights — so its floor at 257 GB/s is about 0.75 ms. It takes
1.79 ms. But no engine is saturated: DMA 66%, Tensor 55%, Scalar 60%. When nothing is at 100% and the kernel is still
slow, look at the **counts**: **19,121 matmuls and 19,040 weight loads in one step**, each streaming only 32 columns
(one per stream), plus 3,249 Scalar-Engine activations for tiny norm, RoPE and softmax pieces. Each instruction has a
fixed cost, and there are tens of thousands of them.

**What it means.** The compiler is not doing anything wrong per op; there are just too many small ops. Only a
hand-written kernel can issue fewer, wider instructions — the fused code-predictor kernel later ran a whole frame in
12.6 ms.

### Profile 3 — the codec decoder in bf16

```text
[codec-bf16-b32] device 292669.0 us
    | HBM rd 9803.68 MB wr 4443.90 MB | eff 33 GB/s read
    | DMA 25% TensorE 16% VectorE 44% ScalarE 33% GpSimd 40% (one line, wrapped)
    scalar  ACTIVATE               n=249535  96413.9 us
    gpsimd  TENSOR_SCALAR_ADDR     n= 21182  71174.5 us
    tensor  MATMUL                 n=259939  46518.6 us
    gpsimd  TENSOR_TENSOR          n= 42394  45934.9 us
    vector  CAST                   n=103131  42957.5 us
```

**How to read it.** 293 ms for a 12-frame chunk, 14.2 GB of HBM traffic, but DMA only 25% busy and the Tensor Engine
16% — the matmuls (the convolutions) are not the problem. The time is in element-wise work: 249,535 Scalar-Engine
activations, GpSimd and Vector ops, 103,131 casts. And the traffic is not weights. Grouping the `DmaPacketAggregated`
table by its `spill_type` column:

```text
spill_type   GB
reload      9.44     # HBM -> SBUF: read back stored intermediates
save        4.37     # SBUF -> HBM: intermediates that did not fit
```

**What it means.** 13.8 of the 14.2 GB are **spills**. The codec's SnakeBeta activation, `x + sin²(αx)/β`, runs after
every convolution at audio sample rate; compiled, it is several separate passes over huge tensors, each intermediate
written to HBM and read back. The bf16 build was also only 22% faster than fp32 and lost too much quality (24.9 dB SNR).
The fix had to keep SnakeBeta's intermediates on chip, fused into the convolution that follows — which is what the
codec kernels do: **9.4 ms per frame-batch at 52.6 dB**.

### And the talker

I did not profile the compiled talker. Its timing was enough: 29.6 ms per step against a floor of about 11 ms (2.82 GB
of weights at 257 GB/s) — about 3× off.

### Decision

Talker + code predictor + codec came to **99.2 ms against the 80 ms budget**, and the profiles showed the same pattern
everywhere: data movement and instruction counts, not arithmetic. AWS's NKI-Lib did not help — its MLP kernel failed to
compile on this chip generation and its attention kernels rely on Trainium2-only DMA features. So: replace each stage
with a hand-written <T id="programming/nki">NKI</T> kernel, one at a time, each validated before moving on. (How to read
a kernel's profile is in the guide: [Profiling a kernel](/blog/inf2/programming/profiling/).)

## Step 2: replace each stage with a kernel

**A first kernel to learn the machine.** A fused RMSNorm + linear for decode
([explained line by line](/blog/inf2/programming/first-kernel/)), plus an FP8 variant: 1.4× faster on weights, but
2.6% error per matrix — too lossy for this model, so it stayed opt-in.

**Codec: 37.5 → 9.4 ms, 52.6 dB.** Three kernels fuse each SnakeBeta with the convolution after it
([codec convolutions](/blog/inf2/kernels/codec-convs/)). Two problems the per-block tests surfaced: the Scalar Engine's
`sin` is only valid on [−π, π] while the arguments reach ±142 ([range reduction](/blog/inf2/patterns/sin-range-reduction/)),
and for small channel counts the Vector Engine was the bottleneck, fixed by feeding SnakeBeta's two terms to the
convolution as separate matmuls.

**Code predictor: 32.1 → 12.6 ms**, as accurate as CPU bf16. One kernel per depth step: 5 layers, the KV slot written
in place, norm weight and RoPE folded into one matrix per step
([QK-norm and RoPE as matmuls](/blog/inf2/patterns/qk-norm-rope/)).

**Talker: 29.6 → 22.9 ms, and the first version was 70 ms.** The fused 28-layer step was correct on the first full
run — and more than twice as slow as the compiler. The kernel takes `do_kv_write` / `do_attention` switches, so an
ablation took two runs: **49 of the 70 ms were the KV-cache writes.** The cache stored K dimension-major (ready for
Q·Kᵀ), so each new token needed 128 tiny 16-byte DMA descriptors. Storing K token-major like V made each layer's write a
single scatter DMA; K pages are now transposed on the Tensor Engine when read
([paged KV attention](/blog/inf2/kernels/paged-kv-attention/)). On paper the three kernels now added up to ~45 ms.

## Step 3: plug it into a serving engine

A lockstep engine runs one step per 80 ms frame for 32 streams
([lockstep batching](/blog/inf2/engine/lockstep-batching/)). Integration found the bugs that unit tests could not:

- **Two silent corruptions, caught by the teacher-forced golden test.** The codec kernels dropped the last partial
  tile whenever a chunk was not a multiple of 512 samples (whole-sequence tests passed; streaming audio was at −0.7 dB
  SNR). And padding tokens' KV writes used an "out of bounds" row that was only out of bounds for one layer's *view* of
  the cache — it was block 0 of the next layer, so every step overwrote one stream's first token. After both fixes: talker
  codebook 0 matches fp32 100%, code predictor 96–97%, end of speech on the golden frame.
- **Host sampling: 74 → 19 ms.** The code predictor's 15 sampling round trips per frame went on device.
- **The codec's compiled front had a 28–33 ms fixed cost per call**, regardless of frames: 3.7 GB of HBM reads in about
  371,000 small DMA packets around its transformer state. Two fixes: decode 2 frames every 2 steps
  ([codec chunking](/blog/inf2/engine/codec-chunking/)), and its transformer became a kernel too.
- **p95 time to first audio: 3 seconds.** The cause was a single multi-second step right after warm-up: the serving
  thread called `torch.set_num_threads(1)`, a global that PyTorch's compiler guards on — so every compiled graph
  recompiled on its first real step, stalling every stream for ~2.5 s. Set it once before warm-up: p95 dropped from
  3,056 to 361 ms. The engine now logs a per-phase breakdown for any step over 300 ms, so the next stall explains itself.

One core now ran 32 streams in real time (RTF 0.99).

## Step 4: two cores, 64 streams

With both cores serving, 32 streams each, the first 64-stream load test (`neuron/engine/loadtest.py`: 64 clients,
each streaming a request and sending the next as soon as it finishes, 90 s) came back too slow. (Outputs in this
section are trimmed to the relevant lines and fields; `/stats` JSON is summarised.)

```text
concurrency 64, 96s: 1061 requests ok, 0 errors
    | audio 4984s -> 51.8x real time aggregate
TTFA ms: p50 378 | p90 431 | p95 614 | p99 896 | max 928
steady-state TTFA ms (after the first 10s): p50 375 | p95 426 | p99 445
playback stalls: 99.9% of requests stalled > 50 ms; RTF p50 1.19
/stats  core 0: step_ms p50 86.2  p90 136.2  |  core 1: p50 78.6  p90 133.9
```

**How to read it.** RTF 1.19 means each stream's audio took 1.19 s to generate per second of speech, so playback
stalls (99.9% of requests did). The `/stats` endpoint shows why: a step takes 79–86 ms at the median and ~135 ms at
p90, against an 80 ms budget per frame. Four investigations followed, each ending in another load test.

### 1. Two engines, one Python process

**Observation.** The same engine on *one* core with 32 streams had run at RTF 0.99. Two engines in one process, at the
same 32 streams per core, ran at 1.19 — 20% slower — with identical kernels. So the extra time was not on the device.

**Investigation.** The device kernels are unchanged, so the difference must be host-side: each engine step has
5–8 ms of Python (batch building, sampling, sending audio), the instance has 4 vCPUs, and two engines in one interpreter
share the GIL. Test: one server process per NeuronCore (`NEURON_RT_VISIBLE_CORES=0` and `=1`) behind a small streaming
router.

```text
concurrency 64, 96s: 1143 requests ok, 0 errors
    | audio 5403s -> 56.2x real time aggregate
steady-state TTFA ms (after the first 10s): p50 342 | p95 389 | p99 425
playback stalls: 96.7% of requests stalled > 50 ms; RTF p50 1.09
/stats  core 0: step_ms p50 77.1  p90 124.2  |  core 1: p50 82.1  p90 123.7
```

**Result.** 1.19 → 1.09. Better, still over budget. The next question was where the remaining ~80 ms went — so I added a
per-phase breakdown to `/stats` and went back to profiling one stage at a time.

### 2. The codec's front transformer: a DMA problem in disguise

**Investigation.** The codec was the biggest phase, so I broke one codec call (2 frames for 32 streams) into stages, each
timed with a device sync (`neuron/bench/bench_codec_stream.py`):

```text
B=32 F=2: full chunk 36.7 ms (18.4 ms per frame)
    front pre (compiled)        1.24 ms
    front transformer (NKI)    12.14 ms     <- an 8-layer, 64-token transformer
    front post (compiled)       3.49 ms
    block0 transconv            2.25 ms
    (16 more conv kernels)      0.5 - 2.0 ms each   (summarised)
```

A transformer this small (59 MB of weights, 64 tokens) should take about a millisecond. The first guess — it issues
~8,200 small DMAs per call, so batch them — took it only from 12.1 to 11.3 ms. So I profiled the kernel itself:

```text
[cfront_b32] device 11510.7 us
    | HBM rd 153.66 MB wr 74.58 MB | eff 13 GB/s read
    | DMA 94% TensorE 2% VectorE 27% ScalarE 3% GpSimd 0%   (one line, wrapped)
```

**How to read it.** DMA is 94% busy but moving only 13 GB/s, against 257 GB/s possible: the DMA engines are busy with
*descriptors*, not bytes. The kernel was copying its attention state into a slice, `kall[:, :, 0:R]`, of a wider SBUF
tile — so every partition's destination was strided, and each copy split into 128 × 32 descriptors of ~140 bytes.
Staging through a contiguous tile and copying on chip:

```text
[cfront_b32b] device 3758.5 us
    | HBM rd 153.66 MB wr 74.58 MB | eff 41 GB/s read
    | DMA 25% TensorE 7% VectorE 93% ScalarE 8% GpSimd 1%   (one line, wrapped)
```

Same bytes, 3× faster. Now the **Vector Engine** is the bottleneck (93%) and the Scalar Engine idle (8%), so the staging
copies moved to ScalarE: **3.3 ms**. The whole codec call: **36.7 → 27.9 ms.**

### 3. The code predictor: 31 launches per frame

**Investigation.** The engine's per-phase timings (device-synced) put the code predictor at **18.7 ms** per frame,
but its 16 step kernels alone had benchmarked at **12.6 ms**. The other 6 ms was everything between them: 16 kernel
launches, 15 launches of a small compiled sampler, and the hand-offs between them. Test: one kernel for the whole
frame — 16 depth steps, top-50 sampling and the embedding lookups on chip (`neuron/tests/test_cp_frame.py`, same
random numbers on both paths):

```text
greedy=True:  token agreement 100.0% (first mismatches [])
greedy=False: token agreement 100.0% (first mismatches [])
per-step (16 cp_step + 15 sampler): 19.00 ms per frame (B=32, incl. D2H)
cp_frame (1 launch):                14.33 ms per frame (B=32, incl. D2H)
```

Building it needed two more investigations — two instructions that compile on their own but not on this chip
generation inside the kernel, found by compiling one-instruction probe kernels and then bisecting the sampler with
early returns ([details](/blog/inf2/kernels/cp-frame/)). With both fixes in, the load test:

```text
concurrency 64, 94s: 1437 requests ok, 0 errors
    | audio 6710s -> 71.3x real time aggregate
steady-state TTFA ms (after the first 10s): p50 276 | p95 311 | p99 325
playback stalls: 1.3% of requests stalled > 50 ms; RTF p50 0.88
```

**Result.** Real time: **1.09 → 0.88**.

### 4. Prefill steps and host Python

The new per-phase `/stats` from that run (mean ms per step, core 0):

```text
step_mean 66.33   prefill_steps_pct 30.29
  host: build talker batch     5.51
  codec_head + D2H            21.22    <- waits for the talker
  host: talker sampling        4.73
  code predictor (cp_frame)   15.93
  host: emit audio + finish    2.23
  codec chunk                 14.92
```

**Two leads.** About 30% of steps carry new prompts, and **12.5 ms per step is host Python** (batch build + sampling +
emit).

**Prefill, investigated with the kernel benchmark** (`neuron/bench/bench_talker_step.py`, 32 decode streams):

```text
decode only                                  22.4 ms
+ 1 prompt (64 tokens)                       23.7 ms
+ 8 prompts (8 x 64 = 512 tokens, T=544)     65.4 ms
+ 8 prompts, attention switched off          37.7 ms
```

8 prompts add 43 ms. Switching attention off removes 28 ms (decode and prefill attention together), so most of the cost
is in the layers themselves. Two causes, each confirmed separately:

- **Padding.** Real prompts are 17–32 tokens, padded to 64 — half the prefill work was padding.
- **T = 544.** The profile of the dense layers alone at T = 32 shows one matmul per weight tile per step — 84,368 of
  them. The profile of the 544-token step (attention included) issued 284,544:

  ```text
  [talker_dense] T=32,  attention off   tensor MATMUL n= 84368
  [talker_pack4] T=544, attention on    tensor MATMUL n=284544
  ```

  A matmul's moving tile holds at most 512 tokens, so at T = 544 every weight tile needs a full 512-column matmul
  *plus* a 32-column one — about 84,000 extra matmuls before attention is even counted. A microbenchmark of a single matmul put the cost of that tail at the per-instruction floor:

  ```text
  M= 128 N=   2   133.3 ns per matmul
  M= 128 N= 128   135.1 ns per matmul
  M= 128 N= 512   345.1 ns per matmul
  ```

  86,000 extra ~130 ns matmuls ≈ 11 ms.

The fix for both: **pack prompts back to back into 128-token tiles** (varlen) and cap a step at 3 tiles, so T ≤ 416:

```text
+ 9 prompts (3 packed tiles, T=416)          42.3 ms     (was 65.4 ms for 8)
```

**Host Python, investigated with CPU microbenchmarks** of the exact code paths, single-threaded like the server:

```text
talker sampling, 32 streams:  repetition penalty 0.47 ms | sample 3.16 ms
  -> sample from the top-50 values only:                    0.91 ms
attention metadata (Python loops -> vectorised):
  decode:  1.09 -> 0.14 ms        prefill group:  3.48 -> 0.26 ms
```

With packed prefill and the host fixes, the load test:

```text
concurrency 64, 96s: 1572 requests ok, 0 errors
    | audio 7380s -> 77.1x real time aggregate
TTFA ms: p50 246 | p90 265 | p95 279 | p99 669
steady-state TTFA ms (after the first 10s): p50 245 | p95 267 | p99 279
playback stalls: 0.9% of requests stalled > 50 ms; RTF p50 0.79
/stats  core 0: step_mean 60.2 ms (host 7.4)  |  core 1: step_mean 60.7 ms
```

**Result: RTF 0.79**, 77× real time on one chip, steady-state p99 time to first audio 279 ms.

## The toolkit: how the problems were actually found

Almost every speedup in this project came from a measurement that contradicted what I assumed. The tools, in the order
I reached for them:

| Tool | Question it answers | What it found here |
| --- | --- | --- |
| **fp32 golden outputs + teacher forcing** | is it still correct? | the out-of-bounds padding bug and the dropped partial tiles — both silent, both invisible in unit tests |
| **per-kernel test vs a reference** | is *this kernel* correct? | every kernel, before integration: hidden-state error vs fp32, token agreement, audio SNR |
| **ablation switches in the kernel** | which part of the kernel is slow? | 49 of 70 ms in the talker's KV writes |
| **device profile** (neuron-explorer) | which engine is the bottleneck, and why? | hidden scatters in the compiled CP; DMA-descriptor-bound codec front; Vector Engine at 93% with Scalar at 8% |
| **microbenchmarks** | what does the hardware actually do? | 257 / 508 GB/s HBM; page gathers 243 GB/s via `scalar_offset`, half that via `vector_select`; ~130 ns per small matmul |
| **probe kernels and bisection** | why does this not compile? | two NKI instructions that do not lower on this chip generation, found by compiling them one at a time |
| **per-phase step timing + slow-step log** | where does a serving step's time go? | 12.5 ms of host Python per step; any step over 300 ms, broken down by phase |
| **burst tests** | what does the worst user see? | the start-up burst's three waves of first audio |
| **Python profiler on startup** | why does warm-up take 15 minutes? | 110 s per kernel variant spent re-tracing it just to compute a cache key |

The pattern that kept repeating: the obvious fix was wrong, and a two-minute measurement found the real one. Fewer DMAs
did not speed up the codec front; *bigger descriptors* did. The fused talker was not slow at math; it was slow at
writing 16-byte rows. Warm-up was not compiling; it was tracing Python.

## Five lessons that only bite on Inferentia

1. **Count instructions, not FLOPs.** A matmul with 2 moving columns costs about the same as one with 128, ~130 ns in
   these kernels. → [The matmul cost model](/blog/inf2/performance/matmul-cost/)
2. **A DMA costs its descriptors, not its bytes.** → [DMA engines and descriptors](/blog/inf2/hardware/dma/)
3. **Stay at or below 512 tokens per step**, or every weight block runs a second, short matmul.
   → [Static shape buckets](/blog/inf2/patterns/static-shape-buckets/)
4. **Padding is not free** — a padded page or prompt token costs as much as a real one.
   → [Varlen packed prefill](/blog/inf2/kernels/packed-prefill/)
5. **Global state is part of the compiled graph**, and your cold start is probably Python.
   → [Cold start and the trace cache](/blog/inf2/engine/cold-start-trace-cache/)

## Results

64 concurrent streaming clients, closed loop (each sends its next request when the previous finishes), 90 s, one
inf2.xlarge, 0 errors:

| Metric | Value |
| --- | ---: |
| Real-time factor per stream (p50) | **0.79** |
| Aggregate audio throughput | **77.1× real time** |
| TTFA, steady state (after the first 10 s): p50 / p95 / p99 | **245 / 267 / 279 ms** |
| TTFA, all requests: p50 / p95 / p99 | 246 / 279 / 669 ms |
| Requests with a playback stall > 50 ms | 0.9% |
| Mean engine step per core (budget 80 ms) | 60 ms |

The p99 over all requests comes from the start-up burst — all 64 clients connecting in the same instant, 32 per core,
admitted over three steps. That tail is the main thing still on my list (a codec "replay" trick that gives every new
stream audio one frame sooner is implemented and verified, but not load-tested yet).

Accuracy against the CPU fp32 reference, teacher-forced on golden prompts: the talker's codebook-0 choices match
95–100%, the code predictor's 96–97%, end of speech lands on the golden frame, and the streamed audio matches a
whole-sequence fp32 decode of the same codes at 46–48 dB SNR.
